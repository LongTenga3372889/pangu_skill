# Pangu 客户诉求处理技能包

把「盘古（Pangu）项目客户诉求处理」的标准流程固化下来，约束 AI **先设计、后实现** —— 设计未经人工评审，不允许动手写代码。

适用范围：盘古项目的客户需求 / 功能改动 / 缺陷修复 / 数据修复。

> 本文件面向**使用者**，讲清楚每一步怎么用。
> `SKILL.md` 面向 **AI**，是流程约束本身 —— 想让 AI 按流程办事，把 `SKILL.md` 放进它的技能目录（见第十节）。

## 四、初始化

初始化入口在**项目根目录**，不在各个 skill 目录下（便于后续扩展更多初始化项）。

### 命令一览

| 命令 | 作用 |
|------|------|
| `node init.js` | 运行全部初始化项 |
| `node init.js --list` | 列出可用的初始化项 |
| `node init.js <id>` | 只运行指定项，如 `node init.js sync-local-scripts` |
| `node init.js --check` | 只体检，**不写入任何文件** |
| `node init.js --force` | 覆盖已生成的配置 |
| `node init.js --migrate-from <目录>` | 迁移旧目录的同步状态 |
| `node init.js -h` | 帮助 |

npm 等价写法：`npm run init`、`npm run init:check`、`npm run init:list`

### `sync-local-scripts` 做了什么

依次执行六步，每步都会打印结果：

| # | 步骤 | 说明 |
|---|------|------|
| 1 | Node 版本 | 校验 ≥ 18 |
| 2 | 依赖 | 缺 `mysql2` 时自动 `npm install` |
| 3 | 数据库配置 | **交互式输入，密码不回显**；已存在则跳过 |
| 4 | 输出目录 | 创建 `<项目根>/js/marmot/{埋点脚本,独立脚本}` |
| 5 | 连通性体检 | 实测连接 + 读 `hpfm_tenant` + 两张脚本表计数 |
| 6 | 迁移同步状态 | 仅在指定 `--migrate-from` 时执行 |

初始化全部通过时退出码为 `0`，有未就绪项时为 `1`。

### 从旧目录迁移

如果你之前用固定目录（如 `D:\work\pangu-js`）同步过，**务必带上 `--migrate-from`**：

```bash
node init.js sync-local-scripts --migrate-from "D:\work\pangu-js"
```

它会把旧的 `.sync_state.json` 复制过来。不带的话新目录状态为空，下次同步会**从头全量重拉几万条脚本**。

## 五、五阶段流程

```
输入需求号 → ⓪拉取需求 → ①需求分析 → ②需求设计 → ③技术设计 → ⛔人工评审 → ④技术实现 → ⑤验证交付
```

**核心原则**：设计先行。**未通过人工评审，禁止进入技术实现。**

---

### 阶段 ⓪ 拉取需求

把需求平台上的需求完整拉下来。

| 项 | 内容 |
|----|------|
| **触发** | 你给出需求号，如 `cro-3842` |
| **AI 动作** | `python 拉取需求/pull_requirement.py cro-3842` |
| **产出** | 需求全文 + 截图 OCR + 评论 + 子任务 |
| **完成标志** | 需求内容已完整掌握 |

**首次运行**会提示输入三项，之后复用：

```
账号:    <需求平台账号>
密码:    <输入时不回显>
项目 ID: <Choerodon 项目 ID>
```

这些保存在 `拉取需求/requirement-config.json`（**已 gitignore**）。Token 有效期约 24 小时，过期会自动重新登录。

**不传需求号**时拉取全部需求列表：

```bash
python 拉取需求/pull_requirement.py
```

**输出内容**（全部打印到终端，**不落盘**）：

- 需求编号 / 标题 / 类型 / 状态 / 优先级
- 报告人 / 负责人 / 创建时间 / 最后更新
- 需求描述（HTML 自动转纯文本）
- **截图 OCR 文本** —— 图片在内存中识别后即丢弃，不保存
- 评论列表、子任务列表

> 截图里的文字往往藏着关键信息（报错、表名、期望效果），OCR 是自动做的，不用你手动看图。

---

### 阶段 ① 需求分析 —— 搞清楚「要什么」

| 项 | 内容 |
|----|------|
| **AI 动作** | 基于拉取到的需求追问：哪个租户？哪个服务/模块？什么业务场景？现状是什么？ |
| **产出** | 一句话需求结论 + 背景 + 期望效果 |
| **完成标志** | 需求清晰、无歧义、**双方认可** |

**你要做的**：回答 AI 的追问，确认它理解得对不对。这一步宁可多问几句 —— 需求理解错了，后面全白做。

---

### 阶段 ② 需求设计 —— 定义「做什么」

| 项 | 内容 |
|----|------|
| **AI 动作** | 把诉求转成功能边界：功能点、影响范围、**不做的事**、验收标准 |
| **产出** | 需求设计说明（功能点 + 边界 + 验收标准） |
| **完成标志** | 功能边界清晰 |

**你要做的**：重点看「不做的事」—— 边界划得对不对，决定了后面会不会跑偏。

---

### 阶段 ③ 技术设计 —— 设计「怎么做」

| 项 | 内容 |
|----|------|
| **AI 动作** | 查证代码库与表结构（**不瞎猜**），确定影响服务、涉及表/字段、实现方式、变更隔离方案 |
| **产出** | 技术方案（固定格式，见下） |
| **完成标志** | 方案完整、可评审 |

AI 必须综合以下**三方面交叉验证**，缺一不可：

1. **Skill 知识** —— 加载 `marmot-script`、`pangu` 等技能，获取方法论与 API 用法
2. **代码** —— Java 源码：服务、Controller/Service 调用链、Feign 远程调用、实体类
3. **数据库字典** —— 表名、字段、关联关系、schema 归属

> 只读代码、只查表、只靠 skill，任何单一来源都可能导致误判。

**技术方案固定格式**：

```
1. 需求概述
2. 影响范围（服务 / 模块 / 表 / 字段）
3. 实现方式及理由（Java二开 / MarmotScript / 数据修复）
4. 关键改动点（具体到类 / 表 / 脚本位置）
5. 变更隔离与回滚方案
6. 风险点
```

---

### ⛔ 人工评审 —— 门禁

**这里是硬性卡点，必须由人拍板。**

| 项 | 内容 |
|----|------|
| **触发** | 技术方案产出后，AI **必须停下**等你判断 |
| **你评审什么** | 影响范围对不对、实现方式选得对不对、**有无污染标准产品的风险** |
| **通过** | 进入技术实现 |
| **不通过** | 方案不合理 → 退回阶段 ③ 重做；需求理解错 → 退回阶段 ① 重新分析 |

> **红线**：未通过评审，禁止写任何实现代码。
> 如果 AI 没停下就直接动手了，拦住它 —— 这是流程故障，不是它「效率高」。

---

### 阶段 ④ 技术实现 —— 评审通过后才动手

| 项 | 内容 |
|----|------|
| **AI 动作** | 按技术方案实施：写代码 / 写脚本 / 生成修复 SQL |
| **约束** | 严格按方案执行，**偏离方案需回到评审** |

**实现方式如何选择**：

| 你的表述 | 实现方式 | 落地位置 |
|---------|---------|---------|
| 「使用脚本实现」/「用 MarmotScript」/「写个脚本」 | MarmotScript | `{服务}/src/main/resources/js/` |
| 未明确说脚本实现 | Java 二开 | 独立租户模块（`scope=provided`） |
| 「数据修复」/「回填」/「修数据」 | data-repair | 生成修复 SQL |

> 一句话说清：**你没说「用脚本」，AI 就不该擅自用脚本替代 Java 改动。**

---

### 阶段 ⑤ 验证交付

| 项 | 内容 |
|----|------|
| **AI 动作** | 编译 / 语法检查、逻辑自测、核对数据 |
| **产出** | 变更说明 + 交付物 |

**交付物直接输出到对话，不生成临时文件。**

## 六、辅助工具：拉取脚本

把 dev 数据库里的 Marmot 脚本同步到本地，方便查证现有实现（阶段 ③ 常要用）。

### 同步到哪里

默认输出到 **`<技能仓库根>/js/marmot/`** —— 与技能同仓库，仓库克隆到哪、输出就跟到哪。

| 项 | 值 |
|----|-----|
| 默认目录 | `<技能仓库根>/js/marmot/` |
| 目录判定 | 由脚本自身位置推导（`__dirname`），**不写死任何绝对路径** |
| 受执行目录影响 | **否**，从任何目录执行结果都一致 |
| 临时改到别处 | 环境变量 `PANGU_JS_DIR` |
| 长期改到别处 | `拉取脚本/sync-config.json`（可选，机器相关，已 gitignore） |

> **为什么不用「从 cwd 向上找 `.git`」**：盘古是多仓库工作区 —— 工作区根目录下 66 个子目录中有 64 个**各自持有 `.git`**。
> 靠 `.git` 向上查找时，在 `small-order` 里执行就会把脚本写到 `small-order\js\marmot`，散落各处。
> 改为从**脚本自身位置**推导后，输出位置完全确定，且不需要任何配置。

同步后的结构：

```
<技能仓库根>/js/marmot/
├── 埋点脚本/<租户名>(<租户号>)/<脚本编码>.js
└── 独立脚本/<租户名>(<租户号>)/<脚本编码>.js
```

> 脚本启动时会打印**实际输出目录**和**解析来源**，执行前核对一眼即可。
> 本仓库的输出目录已被 `.gitignore` 忽略，不会误提交。

### 命令

```bash
# 在目标项目根目录下执行
node 拉取脚本/sync_scripts.js           # 日常增量同步
node 拉取脚本/sync_scripts.js --force   # 强制全量覆盖

# 或在技能目录内用 npm 脚本（等价）
cd 拉取脚本 && npm run sync
cd 拉取脚本 && npm run sync:force
```

### 同步逻辑

- **默认增量**：按 `.sync_state.json` 中 `_meta.lastSyncTime` 只拉新变更
- **版本比较**：`object_version_number` 更高的才写盘
- 建议每月/每季度跑一次 `--force` 确保一致性

### 数据来源

| 类型 | 表 | 内容字段 | 编码字段 | 租户字段 |
|------|-----|---------|---------|---------|
| 埋点脚本 | `spfm_rel_table_record WHERE table_code='sada_buried_point'` | `longValue1` | `value1` | `value3` |
| 独立脚本 | `spfm_rel_table_record WHERE table_code='marmot_script_library'` | `longValue5` | `value3` | `value2` |

租户名称来自 `hpfm_tenant` 表。

## 七、配置说明

### 数据库配置（拉取脚本）

**凭据不写在代码里，也不写在 SKILL.md 里。** 两种方式任选其一。

**方式一：本地配置文件（推荐）**

```bash
cp 拉取脚本/db-config.example.json 拉取脚本/db-config.json
```

然后填入：

```json
{
  "host": "数据库地址",
  "port": 3306,
  "user": "用户名",
  "password": "密码",
  "database": "库名"
}
```

或直接跑 `node init.js`，它会交互式引导你填（**密码不回显**）。

**方式二：环境变量**（优先级高于配置文件）

| 环境变量 | 对应字段 |
|---------|---------|
| `PANGU_DB_HOST` | host |
| `PANGU_DB_PORT` | port（默认 3306） |
| `PANGU_DB_USER` | user |
| `PANGU_DB_PASSWORD` | password |
| `PANGU_DB_NAME` | database |

缺少必填项时脚本会**直接报错退出**，不会静默连到错误的库。

### 输出位置配置（拉取脚本）

**默认无需配置。** 脚本输出到自身所在仓库的 `js/marmot/`，任何地方都不写绝对路径。

需要改到别处时二选一：

- **临时**：设环境变量 `PANGU_JS_DIR` 指向目标目录
- **长期**：复制 `拉取脚本/sync-config.example.json` 为 `sync-config.json` 并填 `projectRoot`
  （该文件已 gitignore —— 里面是机器相关的路径，提交上去对别人是错的）

### 需求平台配置（拉取需求）

首次跑 `pull_requirement.py` 时交互式输入，自动保存到 `拉取需求/requirement-config.json`。

## 八、安全红线

1. **凭据文件禁止提交**
   `拉取脚本/db-config.json`、`拉取需求/requirement-config.json` 含**明文密码**，已在 `.gitignore` 中。
   提交前务必确认：`git status --porcelain` 里不该出现它们。

2. **不瞎猜**
   表名 / 字段 / 类名必须查证，一切以代码库为准。

3. **不污染标准产品**
   二开必须隔离、可追溯、可回滚。

4. **不越门禁**
   未评审通过，不写任何实现代码。

5. **不落盘交付**
   交付物（脚本 / SQL / 方案）直接输出到对话，不生成文件。

## 九、常见问题

**Q：AI 没走流程，拿到需求就开始写代码怎么办？**
A：拦住它。把 `SKILL.md` 放进它的技能目录（见第十节），门禁才会生效。

**Q：`node init.js` 报「未找到 mysql2」？**
A：`--check` 模式不会自动安装。跑一次不带 `--check` 的 `node init.js`，或在 `拉取脚本/` 下执行 `npm install`。

**Q：脚本写到了错误的目录？**
A：默认输出到**技能仓库自己的** `js/marmot/`，与执行目录无关。若你创建过 `拉取脚本/sync-config.json` 或设过 `PANGU_JS_DIR`，检查那里的设置。

**Q：换了目录后同步变慢了？**
A：`.sync_state.json` 跟着输出目录走，换目录等于状态清零 → 触发全量。用 `--migrate-from` 迁移旧状态可避免。

**Q：拉取需求时登录失败？**
A：确认账号密码正确、项目 ID 填写无误。删掉 `拉取需求/requirement-config.json` 里的 `token` 字段可强制重新登录。

## 十、让 AI 用上这些技能

`SKILL.md` 是纯 Markdown 技能描述。DSH 按以下路径发现技能（**深度固定 2 层**，不再往下递归）：

| 优先级 | 路径 |
|--------|------|
| 1 | `<项目根>/.dsh/skills/<名称>/SKILL.md` |
| 2 | `<项目根>/.agents/skills/<名称>/SKILL.md` |
| 3 | `$DSH_HOME/skills/<名称>/SKILL.md` |
| 4 | `~/.agents/skills/<名称>/SKILL.md` |

**SKILL.md 必须带 YAML frontmatter**，且含 `name` 和 `description`，否则会被**静默忽略**（只在日志留一行警告）：

```markdown
---
name: my-skill
description: 一句话说明做什么、什么时候该用
---
```

`name` 必须是小写 kebab-case（`^[a-z0-9]+(?:-[a-z0-9]+)*$`）。

### 当前状态

| 文件 | frontmatter | 可直接加载 |
|------|------------|-----------|
| `拉取脚本/SKILL.md` | ✅ | ✅ |
| `SKILL.md`（主技能） | ❌ 缺失 | ❌ 需先补 |
| `拉取需求/SKILL.md` | ❌ 缺失 | ❌ 需先补 |

另外，本仓库依赖的外部技能 `marmot-script`、`pangu`、`data-repair` **不在本仓库内**，需另行提供。

## 十一、已知限制

- **脚本文件名大小写冲突**：Windows 文件系统不区分大小写。若数据库中两条脚本记录编码仅大小写不同（如 `test` / `TEST`），会写入同一个 `.js` 文件并互相覆盖，导致静默丢数据。已在现有数据中观测到该情况。
- **增量同步存在时间窗口**：`lastSyncTime` 取的是写盘完成时间而非查询发起时间，极端情况下可能漏掉该窗口内的变更。
- **`--force` 无二次确认**：会直接覆盖本地全部脚本文件，执行前请确认已无未同步的本地修改。
- **主技能尚未接入 DSH**：根目录 `SKILL.md` 与 `拉取需求/SKILL.md` 缺 frontmatter，且尚未放入 `.dsh/skills/`。
